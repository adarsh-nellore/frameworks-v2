The Problem

Every journey map ends up as a 60-rectangle Figma file — and breaks the moment anything changes.

Problem frame · before screenshot

The artifact is valuable. The way it's built is the problem.

Strategists I spoke with rebuild the same journey-map skeleton — stages across the top, dimensions down the side — from scratch for every project. Adding a stage means re-measuring rectangles. Switching from B2B SaaS to healthcare means rewriting the rows. The output reads great on a slide and collapses under the first revision.

Research

Three patterns — not "too many clicks" — that explain why.

Finding · Shape
Every journey map is the same grid. The content changes; the primitive doesn't.
Eleven strategists, eleven file structures — all resolving to stages × rows × cells. No one was building anything structurally new; they were redrawing the grid.
Finding · Reuse
Rows are the reusable unit. Stages are the thing strategists wrote from scratch.
"Thinking / Feeling / Doing" shows up in 8 of 11 files. But stages — because they're tied to the specific journey — never copied. Any tool that pre-writes stages in a generic way gets ignored.
Finding · Revision
Stakeholder feedback almost always rearranges — not rewrites — the map.
"Can we move onboarding before discovery?" "What if we split trial into two stages?" The operation is reordering, not editing copy. But in Figma, reordering means remeasuring every rectangle downstream.

Click through the tabs — the research is itself a tiny three-cell journey.

Synthesizing eleven interviews surfaced three patterns that each pointed at the same design move: treat the map as data, not a drawing. Shape tells us the primitive is universal. Reuse tells us what's worth pre-populating. Revision tells us the core operation is reordering — which maps cleanly onto array manipulation and nothing to do with pixel coordinates.

The Primitive

Stages × rows × cells — a flat grid that reorders in one array mutation.

Shape diagram · stages × rows × cells

The map is three arrays. Everything else — layout, theming, export — is a view on top of them.

A JourneyMap is a JSON object with stages, rows, and flat cells that look up by (stageId, rowId). Adding a stage is pushing to the stages array. Reordering is swapping indices. The renderer is a dumb CSS grid that takes those arrays and draws them.

Design

A canvas built for reordering, not drawing.

Canvas · journey map builder

Rows carry their own color lane. Cells inherit. The underlying grid is invisible until you need it.

Lanes are tokenized by row kind (behavior, emotion, opportunity, system) so a strategist can retheme the entire map by swapping a palette JSON. The grid lines are de-emphasized; the color language carries the structure visually.

AI Copilot

"Move onboarding before discovery" is a tool call, not a click storm.

Arrange agent · natural language → map mutation

The arrange agent takes the current map + an instruction and returns a revised map — not a diff, the whole thing.

I used Claude's structured tool-use to define the map shape as the response schema. The model can only return a valid JourneyMap — which means "illegal" edits (missing cells, broken row references) are impossible by construction. Preset chips in the toolbar ("flip emotion with behavior," "add a pre-awareness stage") hit the same endpoint.

Theming

Every map ships with its own palette JSON — portable, reviewable, diff-able.

Theme editor · palette import/export

Teams can ship a house theme the same way they'd ship a design token file.

Chrome colors, canvas washes, glass, shadows, and per-row-kind lane colors are all driven by CSS variables on :root. Import a theme.v1.json, reset to defaults, or export a handoff bundle (map + theme + readme) as one file.

Reflections

What worked, what I'd rebuild, and what the primitive makes possible next.

Roadmap · what's next

Treating the map as data unlocked every feature I built after the first week.

Export, AI arrange, theming, drag-to-rearrange — none of them required touching the renderer. That's the payoff of a strong primitive. What I'd rebuild: the row-kind taxonomy is too tight. "Behavior" collapses three distinct things strategists actually care about (doing, deciding, switching). V2 breaks that apart. Next up: config-driven generation from a persona brief, and live customer-data inputs that auto-populate cells.
